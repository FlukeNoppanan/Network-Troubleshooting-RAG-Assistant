OSPF Neighbor Formation และ EXSTART/EXCHANGE Troubleshooting
OSPF เป็น link-state routing protocol ใช้ IP protocol 89 ไม่ใช่ TCP/UDP port Router แลก Hello และข้อมูล topology เพื่อคำนวณ shortest path ภายใน area ต้องมี Layer 3 reachability และ interface ที่เปิด OSPF ก่อน Router ID ต้องไม่ซ้ำกัน OSPF cost ใช้ตัดสินเส้นทางตามค่าที่ตั้งหรือ reference bandwidth จึงต้องสอดคล้องกันในระบบเพื่อให้เลือกเส้นทางตามต้องการ

เงื่อนไขการเกิด neighbor
ตรวจ subnet, area ID, network type, hello/dead timers, authentication และ stub-area options ให้เข้ากัน Router ที่ passive interface จะไม่ส่ง Hello เพื่อสร้าง neighbor ตรวจ packet capture ว่าเห็น Hello ทั้งขาเข้าและออกหรือไม่ ACL ต้องอนุญาต OSPF protocol 89 และ multicast ที่เกี่ยวข้องบน segment โดย Ethernet broadcast ใช้ 224.0.0.5 และ 224.0.0.6 ตามบทบาท การ ping ผ่านได้ไม่ยืนยันว่า OSPF packet ผ่าน

DR/BDR และ neighbor states
บน broadcast network เลือก Designated Router และ Backup Designated Router เพื่อลดจำนวน adjacency Down คือยังไม่มี Hello, Init คือได้รับ Hello แต่ยังไม่เห็น Router ID ตนเองใน neighbor list, 2-Way คือสื่อสารสองทางแล้ว ระหว่าง DROTHER สองตัวบน broadcast network อาจคง 2-Way ตามปกติ ExStart เจรจา database exchange; Exchange แลก Database Description; Loading ขอ link-state เพิ่ม; Full คือ database synchronized อย่าบังคับทุก neighbor ให้ Full โดยไม่ดู network type และ role

OSPF Neighbor ค้างอยู่ที่ EXSTART: MTU mismatch และ master/slave negotiation
EXSTART เป็นขั้นเจรจา master/slave และ DBD sequence number ก่อนแลกฐานข้อมูล Router ID ที่สูงกว่าเป็น master หาก MTU ของสอง interface ไม่ตรงกัน peer อาจปฏิเสธ Database Description (DBD) ทำให้ค้าง EXSTART หรือ EXCHANGE ต้องตรวจ MTU ทั้งสองฝั่ง ไม่สรุปสาเหตุจาก state อย่างเดียว Router ID ซ้ำหรือ packet loss ก็รบกวนการแลก DBD ได้

OSPF EXSTART/EXCHANGE: วิธีตรวจสอบ
บน Cisco IOS ใช้ show ip ospf neighbor และ show ip ospf interface เพื่อดู state, Router ID และ MTU จับ packet ตรวจ DBD, sequence number, MTU และการส่งซ้ำ ตรวจ link errors และ filter ของ IP protocol 89 ถ้า MTU mismatch ให้ปรับตามข้อกำหนดเส้นทางจริง mtu-ignore ข้ามการตรวจ DBD MTU แต่ไม่แก้ data-plane MTU จึงไม่ควรใช้เพื่อกลบสาเหตุ

แยก EXSTART ออกจากปัญหา Hello
Hello/Dead timer mismatch, area mismatch และ authentication mismatch มักทำให้ neighbor ไม่เกิดหรือไม่ก้าวถึงการแลก DBD ให้ตรวจค่าเหล่านี้เมื่อไม่มี adjacency หรือมี log บ่งชี้ แต่ไม่กล่าวว่าทุกกรณีเป็นสาเหตุเฉพาะของ EXSTART หากเห็น Hello สองทางแล้ว ให้เน้นตรวจ DBD negotiation, MTU, Router ID และ packet loss ก่อน reset neighbor เก็บหลักฐานและประเมินผลกระทบก่อนเปลี่ยนค่า

มี Full แต่ route ไม่ปรากฏ
ตรวจว่ามี network prefix ใน LSDB, area boundary และ route summarization ดู routing table ว่ามี route อื่นที่ถูกเลือกด้วย administrative preference หรือไม่ ตรวจ cost ที่แต่ละ interface และ return route จากปลายทาง ก่อน clear neighbor ให้เก็บหลักฐาน เพราะการ reset จะกระทบบริการและลบอาการที่ใช้วิเคราะห์ ทดสอบหลังแก้ทั้ง neighbor state, route และ application traffic
